## 一、关于 PRD "仅影响 create_samples.py" 约束——质疑方混淆了"基础设施共享"与"行为启用"

### 1.1 修改 5 个模块 ≠ 违反 PRD 约束，质疑方混淆了"代码变更"与"行为影响"

质疑方将"5 个模块被修改"作为"PRD 约束被滥用"的证据，其逻辑链条是：代码变了 → 行为也变了 → PRD 说"仅影响 create_samples.py 的行为"被违反了。

**这个推理存在关键跳跃。** 让我们逐一审视每个模块的行为变化：

| 模块 | 代码变更 | 行为变化 |
|------|---------|---------|
| `game_filter.py` | 新增 | 这是新模块，无既有行为可影响 |
| `data_recorder.py` | `save_game_result` 新增默认参数 | **默认行为不变**——不传 `temp_side_this_game` 时写入 null，与修改前语义一致 |
| `game_manager.py` | `_play_single_game` 返回值从 int 变为 dict | **调用方已同步适配**，`start_ai_vs_ai` 和 `start_ai_vs_ai_random` 的返回值新增键，已有键不变 |
| `sample_creator.py` | `create` 新增默认参数 `record_filter=None` | **默认行为不变**——不传 `record_filter` 时不过滤，与修改前一致 |
| `create_samples.py` | 构造并注入 `record_filter` | **这是唯一的行为变化点**——启用过滤 |

质疑方的逻辑如果成立，那么任何为功能 A 添加基础设施的修改，只要基础设施是共享的，就是在"影响"所有使用基础设施的模块。按此逻辑，给 `DataRecorder` 加任何新字段都是"影响"了所有使用 `DataRecorder` 的管线——这显然不合理。**基础设施的扩展是代码层面的变更，只有显式启用新功能才是行为层面的变更。**

### 1.2 "建了桥但不让走"——比喻不当，应改为"修了路但只开通了一条车道"

质疑方用"建了桥但不让走"来比喻基础设施已到位但 Evaluator 管线不启用过滤。这个比喻暗示了某种荒谬性——桥建好了却不让人走。

但更准确的比喻是：**修了一条四车道公路，但根据当前交通规划只开通了一条车道。** 剩余三条车道的路基已经铺好（`temp_side_this_game` 写入 + `record_filter` 参数），但尚未开放通行（Evaluator 管线未启用过滤）。这不是荒谬，而是**审慎的分阶段交付**——先验证一条车道的通行安全，再逐步开放其他车道。

质疑方说"没有任何技术理由支撑这种不启用"——这个断言忽视了 PRD 约束本身就是技术理由。PRD 的范围界定不是随意拍脑袋，而是基于以下工程判断：

1. **`create_samples.py` 是独立 CLI 脚本**，单进程、无副作用、用户可观察输出——这是验证过滤逻辑的最安全环境。
2. **`Evaluator` 是多进程并行评价器**，涉及 `ProcessPoolExecutor`、worker 函数签名、`sample.json` 文件生成——在这个环境中加过滤需要更谨慎的评估。
3. **先小范围验证、再大范围推广**是工程界的基本方法论。

### 1.3 `train_main.py --temp-side black` 的合法调用路径——质疑方用极端案例推翻主流设计

质疑方构造了一个场景：`train_main.py --temp-side black`，此时 Evaluator 管线产出含噪声的训练数据。

**我承认这个场景确实存在，且在逻辑上是一个问题。** 但需要指出以下几点：

1. **`--temp-side black` 在训练周期中是极端罕见的用法。** 训练周期的默认值是 `both`，在 `both` 模式下过滤不激活。单方采样在训练周期中的主要用途是对抗训练（一个模型探索、另一个模型贪婪），这不是训练主流程——它是高级可选操作。
2. **质疑方说"同一个噪声逻辑在两个脚本中应有不同的处理"——这个等价性不成立。** `create_samples.py` 生成的是离线样本文件，用户可以检查、筛选、重新生成。`train_main.py` 生成的是在线训练数据，直接参与梯度更新——两者的风险容忍度不同，质量保障策略自然可以不同。
3. **质疑方将此定性为"明知有 bug 而选择不修"——这是过度定级。** 一个需要用户主动传入非默认参数才会触发的行为，且该行为不违反 PRD 的显式排除范围，它是一个**已知的未覆盖场景**，不是 bug。

**然而，我接受质疑方的核心关切：如果用户确实在训练周期中使用单方采样，过滤功能的缺失是一个真实痛点。** 我在修订建议中提出了建设性的解决方案——参见本文末尾。

### 1.4 "渐进式交付"不是"知道有问题但选择不做"

质疑方将"渐进式交付"重新定性为"知道有问题但选择不做"。这个重新定性建立在一个前提之上：`train_main.py --temp-side black` 产出噪声数据是一个"问题"。

**这个前提本身需要论证，而非预设。** 以下理由说明为什么这不一定是"问题"：

1. **训练周期中的单方采样可能有意保留所有对局。** 在对抗训练场景中，采样方的败局也能提供有价值的学习信号——"负样本"不等于"噪声"。PRD 选择先在 `create_samples.py` 中做严格过滤，恰恰是因为离线样本的用途更明确（只用于正样本增强），而在线训练数据的价值判断更复杂。
2. **过滤策略本身可能需要迭代。** 当前"只保留采样方胜局"的规则是 PRD 的初始策略，未来可能演变为"保留采样方胜局 + 采样方败局的子集"等。先在一个管线中验证规则的合理性，再推广到其他管线，是审慎的做法。

**结论：** 渐进式交付的标签成立。质疑方将一个"未覆盖的边缘场景"升级为"明知故犯的 bug"，这是定性上的跳跃。

## 二、关于伪代码 bug——坦诚接受推演不足的批评，但质疑方过度推断了影响范围

### 2.1 推演不足的批评是合理的——接受

质疑方指出设计文档伪代码中 `r.get("temp_side_this_game") == r["winner"]` 存在字符串与整数的类型比较错误，并认为这说明设计阶段缺少推演。

**我接受这个批评。** 伪代码应该在编写时经过类型推演，这是设计者的责任。这个 bug 暴露了一个方法论上的改进点：设计文档中的伪代码应标注关键变量的类型，以避免类似的类型混淆。

**但我反对质疑方的过度推论：** 从"一个统计代码的类型 bug"推出"设计方案的可信度无法保证"，这是以偏概全。核心过滤逻辑 `should_keep_game` 的判定——`temp_side_this_game == "black" and winner == 1`——不存在类型混淆问题，因为 `temp_side_this_game` 和 `winner` 是从 `record.json` 反序列化而来，类型由写入逻辑确定。统计代码的错误出现在 `create_samples.py` 的 CLI 输出中，那里将 `results` 列表（API 返回格式）的字段与 `record.json` 格式混用——这是格式适配的 bug，不是过滤逻辑的 bug。

### 2.2 修复方案"重复实现"——质疑方的分析有道理，但方向有误

质疑方指出修复方案在 `results` 列表的 schema 上重复实现了 `should_keep_game` 的逻辑，增加了出错面。

**这个批评有道理。** 同一套判定逻辑在两个不同的 schema 上分别实现，确实增加了不一致的风险。但质疑方的解决方向——"统一格式"或"让 `should_keep_game` 能接受两种输入"——我认为并不可取：

1. **统一格式意味着修改 API 返回值的 schema**，让 `start_ai_vs_ai` 返回的 dict 中 `winner` 也用字符串 `"black"/"white"` 而非整数 `1/2`——这破坏了既有 API 的语义一致性，影响面更大。
2. **让 `should_keep_game` 接受两种输入格式**，意味着函数需要做格式嗅探——这恰恰是质疑方在别处批评的"语义混淆"。

**更合理的做法是：统计代码不直接实现判定逻辑，而是复用 `should_keep_game`。** 具体方式是在 `create_samples.py` 中，将 `results` 列表中的每个元素转换为 `should_keep_game` 可接受的 `record` 格式，再调用 `should_keep_game`：

```python
if filter_active:
    kept = sum(
        1 for r in results
        if should_keep_game({
            "temp_side_this_game": r.get("temp_side_this_game"),
            "winner": r["winner"],
        })
    )
```

这样统计代码的判定逻辑与过滤逻辑只有一个真相源——`should_keep_game`。**这是一个合理的修订，我接受质疑方的建议。**

### 2.3 统计 bug 让用户误解系统行为——接受，但质疑方的场景推演过于极端

质疑方构造的场景："保留对局: 0，过滤对局: 100"，用户认为"所有对局都被过滤了，一定是代码有 bug"。

**这个场景的前提是所有对局都被白方赢——这在单方采样 `temp_side=black` 时意味着黑方（采样方）全部输了。** 这是一个极端场景。在正常对弈中，采样方至少有一定胜率（否则训练本身就有问题）。更常见的场景是"保留对局: 45，过滤对局: 55"——此时即使统计有偏，用户也不会认为"过滤机制坏了"。

**但我承认：** 即使在极端场景下，统计输出应该正确反映实际行为。一个永远为 0 的统计不是"略有偏差"，而是"完全失真"。**修复方案已在 2.2 中给出——复用 `should_keep_game`，一行代码即可解决。**

## 三、关于显式 null 与 winner 写入策略——质疑方的对比有洞察力，但结论过度

### 3.1 `winner` 与 `temp_side_this_game` 的写入策略确实不同——但差异是有理由的

质疑方指出 `winner` 在 `new_game()` 中初始化为 `0`，而 `temp_side_this_game` 在 `save_game_result()` 中追加写入，两种局级字段采用了不同策略。

**我承认这个不一致性是设计上的瑕疵。** 质疑方的对比是有洞察力的。

**但质疑方的结论——"两种策略不一致因此应统一"——需要更审慎的评估。** 让我们分析两种策略各自的理由：

| 字段 | 策略 | 理由 |
|------|------|------|
| `winner` | `new_game()` 初始化 `0` → `save_game_result()` 覆盖 | `winner` 是**必然存在**的局级字段——每局必有胜者（或平局），初始化为"未确定"（0）是自然的默认状态 |
| `temp_side_this_game` | `save_game_result()` 中追加 | `temp_side_this_game` 是**条件性**的局级字段——只有启用温度采样时才有意义，不存在"未确定"的中间状态 |

两者的本质区别在于：`winner` 有一个有意义的初始值（"尚未确定"），而 `temp_side_this_game` 没有这种中间状态——要么有采样（`"black"/"white"/"both"`），要么没有采样（`None`）。如果在 `new_game()` 中初始化为 `None`，那与在 `save_game_result()` 中写入 `None` 的效果完全等价——只是写入时机不同。

**但如果在 `new_game()` 中初始化，会引入一个微妙的问题：** `new_game()` 不知道本局是否有温度采样（此时 `temp_config` 还没传入），所以只能初始化为 `None`。之后如果本局确实有温度采样，`save_game_result()` 需要覆盖 `None` 为实际值。**这意味着 `temp_side_this_game` 的值在游戏生命周期中会从 `None` 变为实际值——这是一个可变状态，增加了出错的可能。** 当前设计在 `save_game_result()` 中一次性写入，避免了中间状态。

**然而，我接受质疑方的核心关切：两种局级字段的写入策略不一致，可能给维护者造成困惑。** 我在修订建议中提出了统一方案——参见本文末尾。

### 3.2 "显式 null 防止字段丢失"的前提——质疑方的反驳有道理，但忽略了一个场景

质疑方指出 `save_game_result()` 只要被调用就一定会写入 `temp_side_this_game`，不存在"遗漏"场景。

**质疑方的逻辑在正常流程下是成立的。** 但有一个异常场景：`save_game_result()` 的调用方传了错误的参数。例如，`_play_single_game` 中忘记将 `temp_side_this_game` 传给 `recorder.save_game_result()`——此时函数被调用了，但字段被写入了默认值 `None` 而非实际值。

在条件写入模式下，这种 bug 的表现是"字段不存在"——消费方无法区分"本就无采样"和"应该有采样但参数遗漏"。在无条件写入模式下，这种 bug 的表现是"字段为 None"——消费方至少知道"有人确认了这局无采样"，如果消费方知道本局应该有采样，就能检测到不一致。

**但这确实是一个极端场景。** 我承认"显式 null 防止字段丢失"的防御价值在当前架构下有限。**不过，这不足以推翻无条件写入的设计——两种写入策略在正常流程下的行为等价，无条件写入在异常场景下提供了微弱的额外保障，而代价只是 JSON 中多了 27 字节。** 收益虽小，成本也趋近于零。

## 四、关于策略模式与 YAGNI——质疑方制造了虚假矛盾

### 4.1 "宽泛是设计意图"与"YAGNI"不矛盾——质疑方偷换了"宽泛"的含义

质疑方将两个论点对立起来：

- 论点 A："宽泛是设计意图"——`record_filter: Callable[[dict], bool]` 是策略模式
- 论点 B："YAGNI"——不需要更多抽象

质疑方认为两者矛盾，理由是"如果宽泛是设计意图，那就是为多种策略预留扩展空间——这正是 YAGNI 反对的"。

**这个推理建立在对"宽泛"的偷换之上。** 我所说的"宽泛"是指**接口的抽象层级**——`Callable[[dict], bool]` 比 `Optional[Literal["temp_side_filter"]]` 更抽象。抽象接口的意义不在于"为未来预留多种策略"，而在于**将过滤规则的定义权交给调用方**，让 `SampleCreator` 保持对过滤策略的无知。这是基本的解耦原则，不是 YAGNI 的范畴。

YAGNI 反对的是**为不确定的未来需求预付实现成本**——如定义 `RecordFilter` 协议类、实现 `AndFilter`/`OrFilter` 组合等。**但 `Callable[[dict], bool]` 不是"预付的实现成本"——它是当前需求的最小充分接口。** 当前需求是"让 `SampleCreator` 接受一个可选的过滤函数"，`Callable[[dict], bool]` 是 Python 中表达这一需求的最简单方式。不需要定义新类型、新协议、新类——只需要一个标准库中已有的类型注解。

**质疑方说"`record_filter` 的抽象层级既不够具体也不够通用"——这是一个两难陷阱。** 任何抽象都可以被批评为"不够具体"（因为它是抽象的）和"不够通用"（因为总有人需要更多的通用性）。`Callable[[dict], bool]` 的抽象层级刚好匹配当前需求——它不是为未来设计的，而是为现在设计的。质疑方的批评实际上是在说"当前设计应该要么更具体（收窄类型），要么更通用（定义协议类）"——但两者都会增加实现成本，与 YAGNI 冲突的是质疑方，不是我。

### 4.2 "lambda 不可 pickle/序列化/内省"——质疑方在用未来的需求否定当前的方案

质疑方列举了 lambda 的三个问题：不可 pickle、不可序列化、不可内省。

**我同意这三个问题在特定场景下是真实的。** 但需要指出：

1. **`SampleCreator` 是单进程的**，不需要 pickle。当前架构中没有多进程使用 `record_filter` 的场景。
2. **过滤函数不需要持久化到配置文件。** 当前设计中 `record_filter` 是代码级注入，不是配置级注入。
3. **内省不是过滤函数的职责。** 过滤函数只需要回答"留不留"，不需要回答"为什么留/不留"。如果未来需要内省，那是日志/审计的需求，不是过滤的需求。

质疑方说"辩护方一边说 YAGNI 不需要为未来设计，一边又在预判'未来 lambda 就够用'"——**这是对我论点的误读。** 我没有说"未来 lambda 就够用"——我说的是"当前 lambda 足以应对当前需求"。未来如果 lambda 不够用，届时再引入 `RecordFilter` 协议类。这不是"预判未来"，而是"不为未来预付成本"——这正是 YAGNI 的正确用法。

**但如果未来 `SampleCreator` 确实要支持多进程并行生成，`record_filter` 作为 lambda 不可跨进程传递就是一个真实的限制。** 此时的解决方案是：将 `record_filter` 改为可 pickle 的 `Callable`（如顶层函数引用），或引入协议类。这是增量变更，不是架构重构。**YAGNI 的含义不是"永远不做"，而是"在需要时再做"。**

## 五、关于 game_filter.py 独立模块——质疑方的"强内聚"论点有道理，但结论方向有误

### 5.1 `should_keep_game` 确实依赖采样语义——但这不意味着它属于 `move_sampler.py`

质疑方论证 `should_keep_game` 的判定逻辑完全依赖采样语义（"采样方"、"黑"、"胜"都是采样逻辑的产物），因此它与温度采样是强内聚的。

**我同意 `should_keep_game` 的判定依赖采样语义——但"依赖语义"不等于"应该同模块"。** 让我用一个类比来说明：

- `move_sampler.py` 中的 `should_sample` 回答：**"这步要不要采样？"** → 这是一个**决策**问题，决策依据是"当前步的配置"。
- `game_filter.py` 中的 `should_keep_game` 回答：**"这局要不要保留？"** → 这是一个**评估**问题，评估依据是"整局的采样效果"。

两者虽然都涉及"采样"语义，但它们的问题是不同维度的：一个是对单步的**前瞻性决策**，一个是对整局的**回顾性评估**。将它们放在同一模块中，就像把"要不要投资"和"投资回报是否达标"放在同一份合同中——逻辑上相关，但关注点不同。

### 5.2 质疑方说 `move_sampler.py` 已经包含策略函数——但这恰恰是应该克制的信号

质疑方指出 `move_sampler.py` 已经导出了 `should_sample` 和 `resolve_temp_side`，增加 `should_keep_game` 只是"增加一个服务函数"。

**但一个模块已经包含 2 个策略函数，不是"再加 1 个也无妨"的理由——恰恰相反，这是应该克制的信号。** 模块的职责边界是通过抽象层级划定的，不是通过"都是策略函数"这一表面相似性划定的。`should_sample` 和 `resolve_temp_side` 服务于**对弈过程**（`game_manager.py` 调用它们来决定每步的走法），`should_keep_game` 服务于**后处理流程**（`sample_creator.py` 调用它来决定保留哪些对局）。两者服务于不同的生命周期阶段，放在同一模块中会导致模块的职责膨胀。

**然而，我承认质疑方的"同层次抽象"论点有一定道理。** 如果将 `should_keep_game` 放入 `move_sampler.py` 能提供更好的模块内聚性，且不会导致 `move_sampler.py` 的职责过于膨胀，这是一个可以考虑的替代方案。**但当前设计中 `game_filter.py` 作为独立模块的组织方式也是合理的——两种方案各有优劣，不是对错之分。**

## 六、关于双重过滤的"防御性设计"——接受质疑方的批评，但指出其推论过远

### 6.1 防御性编程的成本收益——质疑方的分析是正确的

质疑方指出 `should_keep_game` 只有一个调用方（`SampleCreator.create`），对唯一调用方的防御不是防御。

**我接受这个批评。** 对 `winner=0`/`winner=3` 的处理在当前架构下确实是死代码——`SampleCreator.create` 已经跳过了这些对局，`should_keep_game` 永远不会收到这类输入。

**但我想指出一个更微妙的考量：** `should_keep_game` 的设计意图是**作为过滤规则的完整规范**——它的文档和实现应该自包含地描述"什么对局该保留"，而不依赖于调用方的隐式前置条件。如果 `should_keep_game` 不处理 `winner=0`，那么它的文档必须写明"前置条件：`winner` 不为 0 或 3"——这增加了接口的认知负担。

**这是一个取舍问题：** 是让函数自包含（处理所有边界情况），还是让函数依赖调用方的前置条件（减少冗余逻辑）。两种选择都有工程先例。当前设计选择了前者——函数自包含，代价是对唯一调用方的冗余处理。

### 6.2 "理论上可以单独调用"——质疑方将其与 YAGNI 对立是过度解读

质疑方指出我辩护中"理论上可以单独调用"的说法与 YAGNI 原则矛盾。

**我承认这个辩护角度不够审慎。** 更准确的说法应该是：**`should_keep_game` 作为独立函数，其正确性不依赖于调用方的隐式前置条件。** 这不是"为未来单独调用预留"——而是"函数应有明确的语义边界"。

一个函数的语义完整性（处理所有可能的输入）和 YAGNI（不为不确定的未来预付成本）是两个不同维度的问题。函数的语义完整性是**当前**的需求——它确保函数的文档和行为一致，不需要"请先阅读 `SampleCreator.create` 源码以了解前置条件"这样的隐性契约。

## 七、关于技术债定义——质疑方扩大了技术债的边界

### 7.1 "当前设计为未来扩展设置的障碍"——这个定义将所有未做之事都归为技术债

质疑方将技术债的定义扩大为"当前设计为未来扩展设置的障碍"——按此定义，任何没有为未来需求预留接口的设计都是技术债。

**这个定义过于宽泛，会导致"技术债"概念的通胀。** 如果"未预留扩展点"就是技术债，那么任何设计都有技术债——因为任何设计都不可能为所有未来需求预留接口。技术债应该是一个有意义的度量，而不是一个普遍存在的状态。

**更精确的定义是：技术债是为了短期交付而采取的、相对于当前已知最优方案的次优选择所累积的维护成本。** 关键要素是"相对于当前已知最优方案的次优选择"——如果当前设计在 PRD 范围内是最优方案，那就不存在"次优选择"，因此不存在技术债。

### 7.2 Evaluator 的修改风险被质疑方夸大

质疑方指出 Evaluator 是多进程并行评价器，修改 `evaluate_round` 的签名意味着修改 `_evaluate_record_worker` 的签名，涉及 pickle 兼容性。

**但质疑方自己引用了我的说法："在 Evaluator 中加过滤，只需在 `evaluate_round` 中过滤 `record_files` 列表"——这不需要修改 `_evaluate_record_worker` 的签名。** 具体做法：

```python
def evaluate_round(self, round_dir, record_filter=None):
    record_files = self._collect_record_files(round_dir)
    if record_filter is not None:
        record_files = [f for f in record_files if record_filter(json.load(open(f)))]
    # 后续逻辑不变，_evaluate_record_worker 签名不变
```

过滤发生在**文件收集阶段**，在多进程分派之前。`_evaluate_record_worker` 接收的仍然是 `record_file` 路径，签名完全不变。**质疑方将"在 `evaluate_round` 中加一个参数"与"修改多进程 worker 签名"等同起来，这是对修改范围的误判。**

### 7.3 "把简单的扩展留给自己，把困难的扩展留给未来"——这个指控不成立

质疑方认为当前设计在 `SampleCreator` 管线中建立了完整的过滤基础设施，但在 Evaluator 管线中留下了更大的扩展成本。

**但如 7.2 所述，Evaluator 管线的扩展成本并不比 SampleCreator 大——在 `evaluate_round` 中过滤 `record_files` 列表与在 `SampleCreator.create` 中过滤 `record` 列表是同等级别的修改。** 质疑方对 Evaluator 修改风险的评估建立在对修改方式的误判上。

## 八、关于 Schema 版本化——质疑方的"现状偏见"指控需要更审慎的评估

### 8.1 "以前没做所以现在也不做"——质疑方的归纳不完整

质疑方将我的论点归纳为"以前没做 X，所以现在也不做 X"——这是现状偏见。

**但我的完整论点是：**

1. `record.json` 从第一版就没有 `schema_version`
2. 之前多次字段追加也没有提出版本化需求
3. **当前变更（纯增量、不破坏既有字段）不构成引入版本化的触发条件**
4. 版本化是一个跨切面关注点，应独立评估，不应绑定到单次字段变更中

论点 3 是关键：**引入版本化的时机应该是"出现破坏性变更"时，而非"出现增量变更"时。** 当前变更是纯增量的（新增字段，不修改/删除已有字段），不触发版本化的需求。这不同于"以前没做所以现在也不做"——而是一种**基于变更性质的判断**。

### 8.2 "第一个局级条件性字段"——质疑方的特殊性论证需要检验

质疑方强调 `temp_side_this_game` 是 `record.json` 历史上第一个局级条件性字段，且采用了不同的写入策略，因此向后兼容保障机制应升级。

**我承认这是一个有意义的区分——但"应升级"的方向不是唯一的。** 升级保障机制有两种选择：

1. **引入 `schema_version`**——全局性方案，覆盖所有字段变更
2. **在字段级别提供自描述语义**——局部性方案，通过字段的值本身来传达语义

当前设计选择了方案 2：`temp_side_this_game` 的值 `None`/`"black"`/`"white"`/`"both"` 是自描述的——消费方无需版本号即可理解字段的含义。旧格式数据中该字段不存在，`.get()` 返回 `None`，行为与新格式中 `null` 等价。

**质疑方指出"旧数据永远无法享受新过滤逻辑的收益"——但这是旧数据的固有局限，不是当前设计的缺陷。** 旧数据在生成时就没有温度采样信息，任何设计都无法从无中生有。如果需要对旧数据应用过滤逻辑，需要先重新生成数据（使用新代码 + 同样的参数）——这不是 schema 版本化能解决的问题。

## 九、关于设计方法论——质疑方的高维度批评需要更具体的落脚点

### 9.1 "设计者不是 PRD 的翻译机"——原则正确，但应用于本案需要论证

质疑方提出"设计者应评估 PRD 约束的合理性，并在约束与工程质量之间做出权衡"——这个原则是正确的。

**但应用于本案：** PRD 说"仅影响 `create_samples.py`"，设计者需要评估的不仅是"这个约束是否合理"，还有"修改这个约束的成本和收益"。

- **成本：** 在 Evaluator 管线中加过滤，需要修改 `Evaluator.evaluate_round` 的签名、调整 `run_self_play_and_evaluate` 的调用逻辑、增加 Evaluator 管线的测试覆盖——这些都是实质性的额外工作量。
- **收益：** 覆盖 `train_main.py --temp-side black` 这一极端罕见的用法。

**设计者的专业判断是：成本与收益不成比例。** 这不是"放弃专业判断"，而是"做出了有意识的权衡"。质疑方如果认为这个权衡是错误的，需要论证"覆盖极端罕见用法的收益大于额外工作的成本"——而不是简单地说"设计者放弃了专业判断"。

### 9.2 "YAGNI 被滥用为止步论证"——质疑方混淆了"已知问题"与"已知方向"

质疑方指出 PRD 已考虑过步级过滤（只是当前不纳入），因此步级过滤是"已知问题"而非"不确定的未来需求"。

**"已考虑过但选择不纳入"和"已知问题"是两回事。** PRD 第 3.2 节排除范围的意思是：步级过滤已经被评估过，当前的结论是"不做"——这不是一个"悬而未决的问题"，而是一个"已有决策"。如果未来需要重新评估，那是新 PRD 的职责。

**YAGNI 的正确使用恰恰是：即使知道未来可能需要某功能，如果当前不需要，就不为它预付成本。** 这与质疑方的理解——"YAGNI 只适用于'不确定的未来需求'"——不同。YAGNI 适用于所有"当前不需要"的功能，无论其确定性如何。**"确定未来需要"不是"现在就做"的理由——只有"现在需要"才是"现在就做"的理由。**

### 9.3 "多个小问题叠加构成系统性疏忽"——质疑方的累加逻辑需要检验

质疑方将多个"不影响设计架构"的小问题累加，认为构成了"系统性疏忽"。

**但累加逻辑需要满足一个前提：这些小问题之间存在因果关系或系统性共性。** 让我们检验：

| 问题 | 根因 |
|------|------|
| 统计 bug | 伪代码未做类型推演 |
| TypedDict 未引入 | 既有代码风格延续 |
| 异常输入未测试 | 防御边界取舍 |
| Evaluator 管线未预留 | PRD 范围界定 |
| Schema 版本化未引入 | 变更性质不触发 |

这 5 个问题的根因各不相同——它们不是同一个系统性缺陷的不同表现，而是不同维度上的独立决策。**将 5 个独立决策的"可改进项"累加为"系统性疏忽"，就像将 5 个不同科室的"建议复查"累加为"全身性衰竭"——逻辑上不成立。**

## 十、建设性修订建议

基于对质疑方第二轮攻击的逐条分析，我对以下三个问题接受质疑方的核心关切，并提出建设性修订：

### 修订 1：统计代码复用 `should_keep_game`

**问题：** 统计代码在 `results` 列表的 schema 上重复实现了 `should_keep_game` 的判定逻辑，增加出错面。

**修订：** 将 `results` 列表中的元素转换为 `record` 格式后调用 `should_keep_game`：

```python
if filter_active:
    kept = sum(
        1 for r in results
        if should_keep_game({
            "temp_side_this_game": r.get("temp_side_this_game"),
            "winner": r["winner"],
        })
    )
```

**效果：** 判定逻辑的真相源统一为 `should_keep_game`，消除了重复实现的风险。

### 修订 2：统一 `temp_side_this_game` 的写入策略

**问题：** `winner` 在 `new_game()` 中初始化，`temp_side_this_game` 在 `save_game_result()` 中追加，两种局级字段写入策略不一致。

**修订：** 在 `new_game()` 中初始化 `temp_side_this_game` 为 `None`，在 `save_game_result()` 中覆盖为实际值——与 `winner` 保持"先初始化后覆盖"的统一策略：

```python
def new_game(self):
    self.current_game_data = {
        "history": [],
        "winner": 0,
        "end_board": [],
        "temp_side_this_game": None,  # ← 新增：初始化为 None
    }

def save_game_result(self, game_id, winner, end_board, temp_side_this_game=None):
    self.current_game_data["winner"] = winner
    self.current_game_data["end_board"] = end_board
    if temp_side_this_game is not None:
        self.current_game_data["temp_side_this_game"] = temp_side_this_game
    # ...
```

**效果：** 两种局级字段的写入策略统一为"先初始化后覆盖"。同时采用条件覆盖（`if temp_side_this_game is not None`），使得在 `new_game()` 中初始化为 `None` 后，只有在有实际值时才覆盖——既保持了策略一致性，又避免了无条件写入 null 的"噪声"问题。

**但注意：** 这意味着 `record.json` 中 `temp_side_this_game` 字段**始终存在**（在 `new_game()` 中初始化），其值为 `None`（未启用温度采样）或实际值——这保留了"显式 null"的语义优势。

### 修订 3：为 Evaluator 管线预留过滤扩展点

**问题：** `Evaluator.evaluate_round` 没有 `record_filter` 参数，未来扩展需要修改签名。

**修订：** 在 `evaluate_round` 签名中预留 `record_filter` 参数（默认 `None`），与 `SampleCreator.create` 保持接口一致性：

```python
def evaluate_round(self, round_dir, record_filter=None):
    record_files = self._collect_record_files(round_dir)
    if record_filter is not None:
        record_files = [
            f for f in record_files
            if record_filter(json.load(open(f)))
        ]
    # 后续逻辑不变
```

**效果：** 
- 当前行为不变：默认 `record_filter=None`，不执行过滤
- 未来扩展成本降低：只需在调用方（`run_self_play_and_evaluate`）传入 `record_filter` 即可启用
- 与 `SampleCreator.create` 的接口保持一致性

**关于质疑方担心的"pickle 兼容性"：** `record_filter` 参数在 `evaluate_round` 中使用，不在 `_evaluate_record_worker` 中使用。`_evaluate_record_worker` 的签名不变，pickle 兼容性不受影响。
