# 对局级样本过滤机制 — 第二轮质疑（深入反驳）

> 审查立场：在辩护方反驳的基础上，暴露其逻辑中的薄弱环节和内在矛盾，从更高维度质疑设计方法论的合理性。

---

## 一、"PRD 显式排除"——辩护方的万能挡箭牌，掩盖了 PRD 自身的矛盾

### 1.1 PRD 说"仅影响 create_samples.py 的行为"，但设计方案修改了 5 个模块

辩护方反复强调 PRD 约束"仅影响 `create_samples.py` 的行为"，以此将 Evaluator 管线无过滤定性为"显式排除而非设计遗漏"。

但请审视设计文档的"变更模块一览"：

| 模块 | 变更类型 |
|------|---------|
| `ai/game_filter.py` | 新增 |
| `ai/data_recorder.py` | 修改 |
| `ai/game_manager.py` | 修改 |
| `ai/sample_creator.py` | 修改 |
| `ai/create_samples.py` | 修改 |

5 个模块被修改，其中 4 个不是 `create_samples.py`。辩护方的辩护策略是区分"行为影响"与"代码变更范围"——"PRD 说的'仅影响行为'，不是说'只改一个文件'"。但这个区分恰恰暴露了辩护方的逻辑漏洞：

**如果"行为影响"可以与"代码变更范围"解耦，那 Evaluator 管线的代码也没有被变更——它的行为确实没变。但问题是，`DataRecorder`、`AIGameManager`、`SampleCreator` 的代码也被改了，它们的行为也变了（`save_game_result` 多了一个参数，`_play_single_game` 返回值类型变了，`create` 多了一个参数）。** 辩护方所谓的"仅影响 `create_samples.py` 的行为"，实际上是"变更了 5 个模块的代码，但只在一个脚本中启用了新功能"。

这就引出了一个更深层的问题：**既然 `DataRecorder` 已经在所有管线上写入了 `temp_side_this_game`，而 `SampleCreator` 已经具备了 `record_filter` 参数，那么过滤的基础设施已经渗透到了所有管线。** 数据已经产生了（`record.json` 里已有 `temp_side_this_game`），过滤能力已经建好了（`record_filter` 参数），但 Evaluator 管线就是不用。这不是"显式排除"，而是**建了桥但不让走**——基础设施已经到位，但刻意不启用，而没有任何技术理由支撑这种不启用。

### 1.2 "训练周期默认 `temp_side=both` 所以过滤不激活"——这是默认行为，不是设计正当性

辩护方的第二个核心论点是："训练周期的温度采样默认是 `both`，在 `both` 模式下过滤本来就不激活。"

这个论点有一个致命漏洞：**默认值不等于不可能值。** `train_main.py --temp-side black` 是完全合法的命令行调用。当用户这样调用时：

1. `SelfPlayCycle.run()` 接收 `temp_config.temp_side="black"`
2. `run_self_play_and_evaluate()` 将 `temp_config` 传给 `AIGameManager.start_ai_vs_ai()`
3. `_play_single_game()` 在每局写入 `temp_side_this_game="black"` 到 `record.json`
4. `Evaluator.evaluate_round()` 对全部对局生成 `sample.json`——**包括贪婪方白胜的"坏样本"**
5. 这些坏样本被 `trainer.train_auto(sample_dirs)` 吞掉，直接参与训练

**此时 PRD 第 2.1 节所述的原理——"贪婪方获胜说明采样探索未能产生更优解，从这类对局学习可能引入噪声"——在训练周期中完全成立。** 同一个 `--temp-side black` 参数，在 `create_samples.py` 中触发过滤，在 `train_main.py` 中却不触发，而噪声的危害逻辑是完全相同的。

辩护方说"这是 PRD 的有意决策"、"渐进式交付是审慎的工程实践"。但"审慎"不应意味着**在已知场景下明知有 bug 而选择不修**。如果 `train_main.py --temp-side black` 产出含噪声的训练数据，那不是"增量需求"，而是**当前设计在合法调用路径上产出了错误结果**。

### 1.3 "渐进式交付"的真正含义被偷换

辩护方引用"渐进式交付"来为 Evaluator 管线不过滤辩护。但渐进式交付的含义是：**先交付核心功能，再扩展到边缘场景。** 这里的核心功能是"单方采样模式下过滤贪婪方胜局"。`create_samples.py` 是核心场景，但 `train_main.py` 使用同样的参数做同样的事情，它不是"边缘场景"——它是**同一功能在不同入口的复现**。

如果辩护方承认 `train_main.py --temp-side black` 产出噪声数据是已知问题，那"渐进式交付"的标签就站不住了——这不是"先不做"，而是"知道有问题但选择不做"。如果辩护方不承认这是问题，那就需要正面回答：**为什么同一组参数、同一套数据、同一个噪声逻辑，在两个脚本中应有不同的处理？**

## 二、"实现级 bug"——设计文档的伪代码出错，暴露的是设计推演的失职

### 2.1 伪代码中的 bug 不是"实现时打错字"，而是设计阶段未推演

辩护方承认统计 bug 的存在，但将其降级为"实现级 bug"，理由是"核心过滤逻辑 `should_keep_game` 是正确的，统计输出只是辅助性的 CLI 打印信息"。

但问题的严重性不在于"统计是否影响过滤"，而在于：**设计文档中的伪代码是错的。** 设计文档第 173 行：

```python
kept = sum(1 for r in results if r.get("temp_side_this_game") == r["winner"])
```

这不是"实现时写错了一行代码"，而是**在设计阶段，编写伪代码时就没有推演过类型**。`r.get("temp_side_this_game")` 返回 `"black"` / `"white"`（字符串），`r["winner"]` 返回 `1` / `2`（整数），字符串 == 整数永远为 `False`——这个 bug 只需要一次心算推演就能发现。

**如果连设计文档中的伪代码都不经过推演，设计方案的可信度如何保证？** 这不是个别笔误，而是设计过程中缺少推演习惯的体现。辩护方说"一行代码即可修复"——但问题的关键不是修复成本，而是**设计者是否认真推演了自己写的伪代码**。如果伪代码不推演，那设计文档中其他看似正确的逻辑，是否也有类似的隐患？

### 2.2 辩护方自己给出的"修复方案"也有问题

辩护方给出的修复方案：

```python
if filter_active:
    kept = sum(
        1 for r in results
        if (r.get("temp_side_this_game") == "black" and r["winner"] == 1)
        or (r.get("temp_side_this_game") == "white" and r["winner"] == 2)
    )
```

这个修复本身又引入了一个微妙的问题：**它把 `should_keep_game` 的判定逻辑在 `create_samples.py` 中重复实现了一遍。** `should_keep_game` 的核心逻辑就是 `temp_side_this_game == "black" and winner == 1` 等——但 `should_keep_game` 接收的是 `record`（`record.json` 格式），而 `kept` 统计使用的是 `results` 列表中的元素（`start_ai_vs_ai` 返回格式）。

辩护方在第一轮辩护中说"两者的 schema 不同是自然的——一个是 API 返回值，一个是持久化格式……不需要统一"。**但正是这种"不需要统一"的态度，导致了同一套判定逻辑需要在两个不同的 schema 上分别实现。** 一次实现已经在设计文档中出了 bug，凭什么相信第二次实现就是对的？

更合理的做法是：让统计代码直接复用 `should_keep_game`——但这要求 `results` 列表中的元素能转换为 `record` 格式，或者 `should_keep_game` 能接受两种输入格式。辩护方否定了"统一格式"的方向，却在实际上需要两次独立实现同一逻辑——这不是减少复杂度，而是**增加了出错面**。

### 2.3 辩护方说"不影响核心过滤逻辑"——但统计 bug 意味着用户看到的统计是错的

辩护方反复强调"统计输出只是辅助性的 CLI 打印信息，不影响训练样本的生成或过滤行为"。这是正确的——但这是站在机器的视角说的。站在**用户**的视角：

1. 用户运行 `python ai/create_samples.py --temp-side black --games 100`
2. 看到："保留对局: 0，过滤对局: 100"
3. 用户结论：**所有对局都被过滤了，没有样本输出——一定是代码有 bug！**

但实际情况可能是：50 局黑胜被保留，50 局白胜被过滤。统计输出告诉用户"保留了 0 局"，与实际行为完全矛盾。用户会认为整个过滤机制是坏的，可能回退到不过滤模式——**这直接导致设计目标（过滤贪婪方胜局）在用户行为层面失效**。

辩护方说"一行代码即可修复"——但"可修复"和"可忽略"是两个概念。一个让用户完全误解系统行为的 bug，不能因为"修复简单"就降级。

## 三、"显式 null 比隐式缺失更安全"——同一类中的自相矛盾

### 3.1 `DataRecorder` 自己的 `record_move` 方法对 strategy/temperature 做了条件写入

这是第一轮已经提出的质疑，辩护方的回应是"局级字段与步级字段性质不同"：

> `strategy`/`temperature` 是每步的元数据——步与步之间可以不同，条件写入是自然的。`temp_side_this_game` 是每局的元数据——是局级的全局属性，无条件写入使得任何读取 `record.json` 的代码都能明确知道"这局有没有采样方"。

**但这个辩护忽略了一个关键事实：`winner` 也是局级字段，而 `winner` 并不是"无条件写入"的。** 查看 `DataRecorder.new_game()`：

```python
self.current_game_data = {
    "history": [],
    "winner": 0,
    "end_board": []
}
```

`winner` 在 `new_game()` 中初始化为 `0`，然后在 `save_game_result()` 中覆盖为实际值。这是"初始化为默认值 + 最终覆盖"的模式——但 `temp_side_this_game` 被提议在 `save_game_result()` 中**新增参数传入**，而不是在 `new_game()` 中初始化。

辩护方说"显式 null 比隐式缺失更安全"——但如果真的追求"显式 null"，那 `temp_side_this_game` 应该和 `winner` 一样在 `new_game()` 中初始化为默认值 `None`，然后在 `save_game_result()` 中覆盖。**设计方案选择的却是在 `save_game_result()` 中通过新增参数传入并写入——这不是"初始化"，而是"追加"。** 两种局级字段（`winner` 和 `temp_side_this_game`）采用了不同的写入策略：一个在 `new_game()` 初始化，一个在 `save_game_result()` 追加。

辩护方说"局级字段与步级字段性质不同"——但现在的问题不是局级 vs 步级，而是**局级字段内部的不一致**。`winner` 是"先初始化后覆盖"，`temp_side_this_game` 是"在保存时追加"。两者同为局级字段，为什么处理方式不同？

### 3.2 "显式 null 防止字段丢失无法诊断"——这个优势在当前架构下不成立

辩护方说："如果写入逻辑出了 bug，本应写入 `"black"` 的字段被遗漏，消费方无法区分'本就无采样'和'应该有采样但字段丢失'。"

这个论证的前提是：字段可能被"遗漏"。但在当前架构中，`temp_side_this_game` 的写入只有一条路径——`save_game_result()` 中的 `current_game_data["temp_side_this_game"] = temp_side_this_game`。只要 `save_game_result()` 被调用，字段就一定会被写入。**不存在"应该写入但被遗漏"的场景——要么整个 `save_game_result()` 没被调用（此时 `record.json` 根本不存在），要么字段一定被写入。**

所以"显式 null 防止字段丢失"的防御目标，在当前架构下是不必要的。而条件写入（`if temp_side_this_game is not None: current_game_data["temp_side_this_game"] = temp_side_this_game`）同样安全，因为字段缺失的含义在消费方 `record.get("temp_side_this_game")` 返回 `None` 时等价于 null。

辩护方的论点在逻辑上是"为了防御一个不可能发生的问题，引入了不必要的设计不一致"。

## 四、"record_filter 是策略模式，YAGNI"——策略模式的开闭原则被架空

### 4.1 辩护方同时论证了"宽泛是设计意图"和"YAGNI"——这两个论点自相矛盾

辩护方对 `record_filter: Callable[[dict], bool]` 的辩护分两路：

1. **宽泛是设计意图**——"SampleCreator 不应关心过滤函数的具体实现，这是标准的策略模式，解耦了过滤规则的定义与使用"。
2. **YAGNI**——"当前 PRD 只有单一过滤规则，不需要组合、链式、条件化过滤"。

**这两个论点自相矛盾。** 如果"宽泛是设计意图"，那设计意图就是为多种过滤策略预留扩展空间——这正是 YAGNI 所反对的。如果"YAGNI"成立，那 `record_filter` 参数根本不应该存在——应该直接在 `SampleCreator.create()` 中硬编码 `should_keep_game` 的逻辑，或者至少把参数类型从 `Callable[[dict], bool]` 收窄为 `Optional[Literal["temp_side_filter"]]`。

辩护方同时举起了"策略模式"（开闭原则）和"YAGNI"（不做多余抽象）两面旗帜，但两面旗帜指向相反的方向。**真正的问题是：`record_filter` 的抽象层级既不够具体（没有约束输入 schema），也不够通用（不支持组合），处于一个两头不讨好的中间地带。** 辩护方无法同时用"足够通用"和"足够精简"来为同一个设计辩护。

### 4.2 "lambda 组合足以应对"——这个断言经不起推敲

辩护方说如果未来需要组合过滤条件，可以用 lambda：

```python
combined_filter = lambda r: should_keep_game(r) and custom_filter(r)
```

但这个方案有以下问题：

1. **lambda 不可 pickle**——如果未来 `SampleCreator` 要支持多进程并行生成（类似 `Evaluator`），`record_filter` 作为 lambda 无法跨进程传递。
2. **lambda 不可序列化**——如果过滤函数需要持久化到配置文件，lambda 无法表达。
3. **lambda 无法内省**——调试时无法打印"当前使用了哪些过滤规则"，`repr(lambda)` 只输出 `<function <lambda> at 0x...>`。

辩护方的"lambda 足以应对"是基于"当前只有单进程、不需要持久化、不需要内省"的假设——但这些假设正是 YAGNI 原则下"不应该预判"的东西。辩护方一边说 YAGNI 不需要为未来设计，一边又在预判"未来 lambda 就够用"——这本身就是对 YAGNI 的违反。

## 五、"game_filter.py 独立模块是对关注点分离的尊重"——但关注点分离不等于文件分离

### 5.1 辩护方说"怎么采"和"采完了怎么用"是不同关注点——但 `should_keep_game` 的判定依赖采样语义

辩护方的核心论证是：`move_sampler.py` 负责"怎么采"（温度变换、加权采样），`game_filter.py` 负责"采完了怎么用"（过滤判定），两者关注点不同。

**但 `should_keep_game` 的判定逻辑完全依赖采样语义：** 它检查 `temp_side_this_game == "black" and winner == 1`——"采样方黑胜"这个判定的每一个成分（"采样方"、"黑"、"胜"）都是采样逻辑的产物。如果没有温度采样，就没有"采样方"的概念，`should_keep_game` 也就没有存在的意义。

`should_keep_game` 不是"采完了怎么用"的通用过滤逻辑，而是**"温度采样质量评估"逻辑**——它与温度采样是强内聚的。将"温度采样的质量评估"与"温度采样的力学实现"放在不同模块中，不是关注点分离，而是**强内聚关系的强制拆散**。

### 5.2 辩护方说"依赖方向不同"——但这个论证建立在对"上层/底层"的主观划分上

辩护方说 `move_sampler.py` 是底层模块（被 `game_manager.py`、`engine.py` 依赖），`should_keep_game` 是上层逻辑（被 `create_samples.py` 消费），放入 `move_sampler.py` 会导致底层感知上层需求。

**但 `move_sampler.py` 已经导出了 `should_sample` 和 `resolve_temp_side`——这两个函数就是被 `game_manager.py`（上层）消费的。** `move_sampler.py` 本身就已经在为上层提供服务，它不是纯粹的"底层不感知上层"的模块。将 `should_keep_game` 放入 `move_sampler.py`，不过是增加了一个服务函数，与 `should_sample` 和 `resolve_temp_side` 形成完整的"温度采样策略函数族"。

辩护方的"依赖方向"论证，建立在对 `move_sampler.py` 角色的主观缩限上——把它定义为"只管力学实现"的底层模块。但实际的 `move_sampler.py` 已经包含了 `should_sample`（策略判定函数）和 `resolve_temp_side`（策略解析函数），它们和 `should_keep_game`（策略评估函数）是同一层次的抽象。**在已经包含策略函数的模块中再加一个策略函数，不是依赖方向倒置，而是职责归位。**

## 六、"双重过滤是防御性设计"——被滥用的防御性编程标签

### 6.1 防御性编程有成本，双重过滤的收益为负

辩护方将 `should_keep_game` 和 `SampleCreator.create()` 都过滤平局定性为"防御性设计"，声称"两个独立的过滤规则各自完备，组合使用时不产生冲突，比假设调用方已做前置过滤更安全"。

**但防御性编程的正当性取决于两个条件：**
1. 前置条件不确定（调用方可能不遵守契约）
2. 防御代码的成本低于未防御时的损失

对于条件 1：`should_keep_game` 只有一个调用方——`SampleCreator.create()`。它不是一个公共 API，没有外部调用者需要防御。在唯一调用方已经做了平局过滤的前提下，`should_keep_game` 对 `winner=0`/`winner=3` 的处理不是"防御"，而是**死代码**。

对于条件 2：双重过滤的成本是**认知负担和维护一致性的风险**。任何修改过滤规则的开发者都需要理解两层过滤之间的关系——"如果我改了 `SampleCreator.create()` 的平局过滤，`should_keep_game` 会怎样？如果两处对平局的定义不一致呢？"这种认知负担是实打实的，而收益是防御一个**不可能发生**的场景（`should_keep_game` 被单独调用且调用方不过滤平局）。

### 6.2 辩护方说 `should_keep_game` 可以"单独调用"——但设计没有提供单独调用的场景

辩护方在 7.3 中说："`should_keep_game` 是独立函数，不假设调用上下文。它可以单独调用，不仅限于 `SampleCreator.create`。"

**但设计方案中没有任何场景需要单独调用 `should_keep_game`。** 它唯一被使用的地方就是 `SampleCreator.create()` 的 `record_filter` 参数。如果设计者预期它会被单独调用，那应该提供调用文档和用例——但设计文档和测试用例都没有涵盖单独调用场景。

辩护方用"理论上可以单独调用"来论证"实际上需要防御性处理"——这是**用假设的未来场景来为当前的过度设计辩护**，与辩护方自己高举的 YAGNI 原则再次矛盾。

---

## 七、"不是技术债，是未实现的未来需求"——对技术债定义的偷换

### 7.1 辩护方对技术债的定义过于狭隘

辩护方说："不在当前 PRD 范围内实现的功能不是'技术债'，而是'未实现的未来需求'。技术债是指为了短期交付而采取的次优方案所累积的维护成本——而当前设计在 PRD 范围内是最优方案。"

**这个定义过于狭隘。** 技术债不仅包括"已采取的次优方案"，还包括**"当前设计为未来扩展设置的障碍"**。具体到本案：

1. `DataRecorder.save_game_result()` 已写入 `temp_side_this_game` 到所有管线的 `record.json`
2. `SampleCreator.create()` 已具备 `record_filter` 参数
3. 但 `Evaluator.evaluate_round()` 没有 `record_filter` 参数

如果未来要在 Evaluator 管线中加过滤，需要修改 `Evaluator`——而 `Evaluator` 是一个多进程并行评价器，修改它的签名和逻辑比修改 `SampleCreator` 风险大得多。辩护方自己在 9.3 中也承认："在 Evaluator 中加过滤，只需在 `evaluate_round` 中过滤 `record_files` 列表"——**但"只需"和"风险可控"是两个概念。** `Evaluator.evaluate_round` 涉及多进程并行执行、`ProcessPoolExecutor`、`_evaluate_record_worker` 顶层函数等，修改它的入参意味着修改 `_evaluate_record_worker` 的签名，而 `ProcessPoolExecutor` 的 worker 函数签名的变更需要特别注意 pickle 兼容性。

当前设计在 `SampleCreator` 管线中建立了完整的过滤基础设施（`should_keep_game` + `record_filter` + `temp_side_this_game` 写入），但在 Evaluator 管线中留下了更大的扩展成本——这不是"最优方案"，而是**把简单的扩展留给自己，把困难的扩展留给未来**。

---

## 八、"Schema 版本化是通用问题"——通用问题不该被借口逃避

### 8.1 辩护方的逻辑是"以前没做，所以现在也不做"——这是现状偏见

辩护方说："`record.json` 从第一版就没有 `schema_version`，之前追加字段时也没有人提出这个问题。如果现在要加 `schema_version`，应该是一个独立的重构任务。"

**这个论证的逻辑是"以前没做 X，所以现在也不做 X"——这是典型的现状偏见（Status Quo Bias）。** 以前没做 `schema_version` 是以前的失误，不能作为现在继续犯同样错误的理由。

更重要的是：**以前追加的字段（`step_id`、`strategy`/`temperature`/`top_k`/`sampling_probs`）都是步级字段，使用条件写入，旧格式数据中字段不存在时消费方通过 `.get()` 返回 `None`，行为自然兼容。** 但 `temp_side_this_game` 是局级字段，使用无条件写入——**这是 `record.json` 历史上第一次写入局级条件性字段，且采用了与以往步级字段不同的写入策略。** 正因为写入策略变了，向后兼容的保障机制也应该升级——至少应该记录"这是第几个版本的字段变更"，而不是继续沿用"以前没做版本化所以现在也不做"的逻辑。

### 8.2 辩护方说"当前所有变更都是纯增量"——但增量变更是有边界的

辩护方说"当前所有变更都是纯增量（新增字段，不修改/删除已有字段），增量变更是天然向后兼容的"。

**这个断言只在消费方只做 `.get()` 读取时成立。** 但 `should_keep_game` 的逻辑依赖于 `temp_side_this_game` 字段的存在和取值——旧格式数据中该字段不存在，`.get()` 返回 `None`，`should_keep_game` 返回 `True`（不过滤）。这是"兼容"的，但**兼容不等于正确**：

- 旧格式数据可能是单方采样模式下生成的（只是当时没有 `temp_side_this_game` 字段），本应被过滤，但因为没有该字段而被保留。
- `should_keep_game` 无法区分"这局确实不是单方采样"和"这局可能是单方采样但数据太旧无法判断"。

辩护方说"旧格式数据通过 `.get()` 返回 `None` 等同于 null 语义，行为与修改前一致"——**"行为与修改前一致"恰恰意味着旧数据永远无法享受新过滤逻辑的收益。** 如果旧数据中有大量单方采样产生的噪声对局，它们不会被过滤，因为 `should_keep_game` 无法识别它们。这不是"兼容"，而是**功能对旧数据的永久失效**。

## 九、更高维度的质疑：设计方法论的问题

### 9.1 辩护方的核心策略是"PRD 说什么就做什么"——但设计不是 PRD 的翻译机

辩护方最常使用的辩护句式是"PRD 明确排除了……"、"PRD 的显式要求是……"。这种辩护策略隐含了一个危险的前提：**设计者的职责仅限于忠实地翻译 PRD，而不包括识别 PRD 中的问题并提出改进建议。**

但设计的职责恰恰是：**在理解 PRD 意图的基础上，评估 PRD 约束的合理性，并在约束与工程质量之间做出权衡。** PRD 说"仅影响 `create_samples.py` 的行为"，设计者应该追问：这个约束是否会导致同一功能在不同入口的行为不一致？如果会，是否应该向 PRD 作者提出修订建议？

**设计者不是 PRD 的执行机器，而是 PRD 的质量把关者。** 辩护方将"PRD 约束"当作免死金牌，实际上放弃了设计者的专业判断责任。

### 9.2 "YAGNI"被滥用为止步论证

辩护方多次使用 YAGNI 原则：不需要步级过滤（YAGNI）、不需要 `RecordFilter` 协议类（YAGNI）、不需要 schema 版本化（YAGNI）、不需要 `TypedDict`（YAGNI）。

**但 YAGNI 的正确使用是"不为不确定的未来需求预付成本"，而不是"不为可预见的扩展预留接口"。** 以下场景是可预见的：

1. **步级过滤**——PRD 第 3.2 节排除范围提到"样本内部过滤（步级过滤）：过滤粒度为对局级"——这说明 PRD 作者已经考虑过步级过滤，只是当前不纳入。这是一个**已知的未来方向**，不是"不确定的未来需求"。
2. **Evaluator 管线过滤**——辩护方自己也承认未来可能需要，只是说"通过新 PRD 追踪"。既然可预见，为什么不在当前设计中做最小化的预留（比如在 `Evaluator.evaluate_round` 的签名中预留 `record_filter` 参数）？
3. **TypedDict**——辩护方承认引入 `NamedTuple` 是合理的，但说"这是实现细节"。**但类型安全不是"实现细节"——它是 API 设计的核心属性。** 如果设计文档不约束返回值类型，那实现者可以自由选择 `dict`、`NamedTuple`、`dataclass` 或 `TypedDict`，而每种选择对调用方的影响完全不同。

辩护方对 YAGNI 的使用，不是"不为不确定的未来预付成本"，而是**"不为已知的问题做任何准备"**——这是 YAGNI 的滥用。

### 9.3 辩护方承认了多处可改进，但每处都说"不影响设计架构"——积累效应被忽视

梳理辩护方的承认清单：

| 辩护方承认 | 但说 |
|-----------|------|
| 统计 bug 存在 | 一行修复，不影响核心逻辑 |
| 引入 NamedTuple 是合理的 | 实现阶段再做 |
| 异常输入测试可以补充 | 实现阶段再做 |
| `TypedDict` 可以增强类型安全 | 实现阶段再做 |
| Evaluator 管线未来可能需要过滤 | 通过新 PRD 追踪 |
| Schema 版本化是好的 | 独立重构任务 |

**每一项单独看都"不影响设计架构"，但所有项加在一起，构成了一个"设计文档不够严谨"的整体图景。** 设计文档的伪代码有 bug，返回值类型未约束，异常输入未考虑，管线扩展未预留，schema 演进未规划——这不是"每个都是小问题"，而是**设计方法论上的系统性疏忽**。

辩护方说"设计方案在 PRD 的范围内是完备的、正确的、可实施的"——但"完备"不等于"只覆盖 PRD 字面要求"，"正确"不等于"伪代码有 bug 但可以修"，"可实施"不等于"实现时需要补一大堆设计文档没考虑的东西"。

## 十、总结：第二轮质疑的核心论点

| # | 质疑点 | 对辩护方反驳的回应 |
|---|--------|-------------------|
| 1 | PRD "仅影响 create_samples.py"不等于"只能在 create_samples.py 启用功能"——基础设施已渗透全管线，刻意不启用没有技术正当性 | 辩护方混淆了"行为范围"与"代码范围" |
| 2 | `train_main.py --temp-side black` 是合法调用路径，产出噪声数据是当前设计的直接后果，不是"未来需求" | 辩护方用"默认值"掩盖"合法调用路径" |
| 3 | 伪代码中的 bug 暴露了设计阶段缺少推演，不是"实现时打错字" | 辩护方将设计失误降级为"实现级 bug" |
| 4 | 修复方案重复实现了 `should_keep_game` 的逻辑，增加了出错面 | 辩护方否定了格式统一，又需要两次独立实现 |
| 5 | `temp_side_this_game` 与 `winner` 同为局级字段但写入策略不同 | 辩护方的"局级 vs 步级"区分不适用 |
| 6 | "显式 null 防止字段丢失"的前提在当前架构下不成立 | 辩护方防御了一个不可能发生的问题 |
| 7 | "策略模式"与"YAGNI"自相矛盾 | 辩护方同时论证"足够通用"和"足够精简" |
| 8 | `should_keep_game` 与温度采样强内聚，不应强制拆散 | 辩护方的"关注点分离"实际上是"强内聚拆散" |
| 9 | "防御性设计"标签被滥用——对唯一调用方的防御不是防御 | 辩护方用假设的未来场景辩护，违反自己的 YAGNI |
| 10 | 设计者不是 PRD 的翻译机，应评估约束合理性 | 辩护方放弃专业判断，将 PRD 约束当作免死金牌 |

**结论：辩护方的核心策略是用"PRD 约束"、"YAGNI"、"实现细节"三面盾牌挡住所有质疑。但这三面盾牌各自有裂缝：PRD 约束被辩护方做了超出其字面含义的延伸解读；YAGNI 被用于否定可预见的扩展需求；"实现细节"被用于回避设计文档自身的质量问题。设计方案在 PRD 字面要求上可能"及格"，但在工程质量上远未达到"可信赖"的标准。建议退回修订，至少解决以下三个核心问题：**

1. **为 Evaluator 管线预留过滤扩展点**（至少在 `evaluate_round` 签名中预留 `record_filter` 参数）
2. **统一 `temp_side_this_game` 的写入策略**（与 `winner` 保持一致，或与 `strategy` 保持一致，二选一）
3. **设计文档中的伪代码必须经过推演验证**，统计代码应复用 `should_keep_game` 而非重复实现判定逻辑
