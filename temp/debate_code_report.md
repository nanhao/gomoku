## 二、核心争议与裁定

### 争议1：架构分层的有效性

| 辩护方观点 | 质疑方观点 |
|-----------|-----------|
| game→ai→app→gui 洋葱模型，单向依赖清晰 | controller.game 被上层直接访问，封装边界被穿透 |
| Controller 是 Facade 模式教科书实现 | "唯一对外接口"名不副实，GUIHelper 直接读取内部属性 |
| app 包是流程编排层（Flow Orchestration） | app 包是无效间接层，只做 dict 翻译 |
| dict 返回格式务实，调用方不需处理异常类型 | dict 返回值无类型契约，每层 schema 不同，"dict 地狱" |

**裁定**：**辩护方基本立场成立，但质疑方指出的问题真实存在。**

- 洋葱分层的基本结构是清晰的，这是项目最大的架构优势
- `controller.game` 被外部访问确实是封装泄漏，但当前仅用于 `is None` 检查，属于"状态探测"而非"业务穿透"，严重程度有限
- app 层的 `GameSession` 确实包含流程编排逻辑（如 `need_ai_move` 标志），但 `GUIHelper` 的大部分方法确实是简单 dict 透传，存在过度包装
- dict 返回值缺乏 `TypedDict` 是真实的技术债务，但在项目当前规模下尚可控

**改进建议**：
1. 为 Controller 添加 `has_game()` 方法，替代外部 `controller.game is None` 检查
2. 考虑用 `dataclass` 或 `TypedDict` 定义关键返回值类型
3. `GUIHelper` 可考虑精简或与 `GameSession` 合并

### 争议2：Evaluator 的可靠性（最核心争议）

| 辩护方观点 | 质疑方观点 |
|-----------|-----------|
| 双向棋型检测法体现了五子棋领域知识 | `_compute_four_reward` 是空壳，for 循环什么都没做 |
| 敌方系数 0.95 符合棋理——进攻优先于防守 | 0.95 系数系统性低估防守，在五子棋中可能致命 |
| blend_rewards 取 max 确保五连追溯信号不被稀释 | 取 max 不是融合而是选择，弱信号被永久丢弃 |
| 五连追溯类似 TD(λ)，0.9 衰减是成熟方法 | 五连追溯只追溯 5 步，无法解决稀疏奖励问题 |

**裁定**：**质疑方胜出。Evaluator 是训练管道的心脏，但其核心逻辑存在严重缺陷。**

关键问题：
1. **`_compute_four_reward` 是空壳**：冲四的 reward 被硬编码为 `0.5 * MAX_REWARD`，与活三完全等价。这不是"技术债务"，是评价器核心逻辑的 bug
2. **`blend_rewards` 取 max 丢弃弱信号**：五连追溯的早期步骤（衰减后奖励很小）的信号被完全丢弃，而早期步骤恰恰是最重要的决策点。`alpha` 参数已预留但未使用
3. **敌方系数 0.95 过低**：在五子棋中，防守活四/冲四的紧迫性往往高于进攻活三，0.95 的系数系统性低估防守价值
4. **`_detect_shape_in_direction` 只检测连续棋型**：无法识别跳活三、跳冲四等非连续棋型，这是五子棋中最常见的战术形态

辩护方的合理观点：
- 双向检测（攻击+防守）的设计方向正确
- 五连追溯的信用分配思路有价值
- Softmax 的数值稳定性处理是正确的

### 争议3：数据闭环是否断裂

| 辩护方观点 | 质疑方观点 |
|-----------|-----------|
| 系统是"教师-学生"范式，自我对弈产生棋局状态分布 | record.json 的 output 字段完全无用，是数据垃圾 |
| Evaluator 的规则标签不是"无意义的曲线拟合" | AI 自我对弈的预测不被用于训练，闭环实际断裂 |
| 监督学习本质就是"标签生成器+曲线拟合" | 训练是"规则引擎生成标签，神经网络做曲线拟合" |

**裁定**：**双方各有道理，但需要澄清术语。**

- 质疑方的事实判断正确：record.json 的 output 字段确实未被 Evaluator 使用，AI 的预测输出不构成训练信号
- 辩护方的定性更准确：这不是"断裂的闭环"，而是"教师-学生"的监督学习范式——自我对弈的价值在于产生棋局状态分布，而非提供训练标签
- 但 `record.json` 中存储 225 维概率向量确实是无意义的存储浪费，应清理或重新设计

**改进建议**：
1. 清理 record.json 中无用的 output 字段，或为未来的策略蒸馏（policy distillation）保留但明确标记
2. 文档中明确说明系统的训练范式：规则评估器生成标签，神经网络拟合规则

### 争议4：CNN 模型的设计缺陷

| 辩护方观点 | 质疑方观点 |
|-----------|-----------|
| 3 通道输入编码是精心设计的 | player_channel 全1/全0 浪费空间通道 |
| BatchNorm 加速训练收敛 | BatchNorm + 方差为0通道 = 信息自毁 |
| 28800→150 压缩是标准做法（类比 ResNet/VGG） | 192 倍维度压缩，卷积特征被暴力抹平 |
| _vector_to_tensor 单下划线是 protected 不是 private | 私有方法被外部类调用违反封装约定 |

**裁定**：**质疑方在技术上更准确，但部分论点过度渲染。**

关键判定：
1. **BatchNorm + 均匀通道确实有缺陷**：当 batch 中所有样本为同一方时，player_channel 方差为 0，BatchNorm 将其坍缩为常数 beta，当前方信息退化为偏置项。辩护方承认这是架构缺陷
2. **28800→150 的压缩并非"标准做法"**：ResNet 用全局平均池化做空间降维，而非直接展平后线性压缩。本项目卷积层无 pooling/stride，特征图尺寸始终 15×15，导致 FC 层输入维度过高，这才是根本问题
3. **_vector_to_tensor 的访问**：Python 的单下划线是约定俗成的 protected 标记，同一包内访问可以接受，但更好的做法是将其提取为公共转换工具

**改进建议**：
1. 在卷积层中加入池化层或 stride>1 的卷积，做空间降维
2. 将 player_channel 从卷积输入中分离，作为全局特征在全连接层注入
3. 或者用 LayerNorm 替代 BatchNorm 处理 player_channel

## 四、辩论中的逻辑交锋亮点

### 亮点1：blend_rewards 的 max 之争

这是三轮辩论中最精彩的交锋：

- **第一轮** 质疑方：取 max 导致五连追溯信号被稀释，与注释矛盾
- **第二轮** 辩护方：质疑方"把代码读反了"！取 max 保留的是更大的信号，加权平均才会使 1000000 减半
- **第三轮** 质疑方：辩护方说"读反了"是误判。质疑方质疑的不是代码行为而是设计语义——取 max 是"选择"不是"融合"，弱信号（五连追溯早期步骤）被永久丢弃。当 shape_reward=500000 而 line_bonus=100 时，max=500000，追溯信号完全丢失

**裁定**：质疑方最终胜出。辩护方在"代码做了什么"上是对的，但质疑方在"代码应该做什么"上是对的——max 不是融合，是选择；保留强信号 ≠ 保留正确的信号。

### 亮点2：数据闭环是否断裂

- **质疑方**：Evaluator 完全不读取 record.json 的 output 字段，AI 预测不被用于训练标签——闭环断裂
- **辩护方**：系统从来就不是"模型输出自我监督的闭环"，而是"教师-学生"范式。自我对弈的价值在于产生棋局状态分布，不是提供训练标签

**裁定**：双方都有道理。质疑方的事实判断正确（output 字段无用），但辩护方的范式定性更准确（监督学习本来就是曲线拟合）。关键改进是清理无用数据、明确文档说明训练范式。

### 亮点3：BatchNorm + 全1通道

- **质疑方**：BatchNorm 会将方差为 0 的通道信息"数值抹除"，CNN 的当前方信息被系统性破坏
- **辩护方**：BatchNorm 在同 batch 同玩家时将通道坍缩为常数 beta，等价于全局偏置——不是"自毁"但确实是架构缺陷

**裁定**：质疑方方向正确但措辞过度（"自毁"太戏剧化），辩护方承认了架构缺陷但淡化了影响。实质问题是：player_channel 的设计本身就不需要空间通道，它应该作为全局特征而非空间通道注入。

## 五、最终评价

### 项目核心价值

1. **架构完整性**：从游戏逻辑 → AI 引擎 → 数据记录 → 评价器 → 训练器 → 模型管理，整个管线是完整的、可运行的
2. **设计意识**：模块职责清晰，BaseModel/BaseTrainer 的抽象层次恰当，分层解耦有明确的设计约束
3. **可迭代性**：当前架构使得替换任何组件成为可能——换评估器、换模型、换训练策略——而不需要重写其他部分
4. **测试覆盖**：20+ 测试文件，有数学构造法等高质量测试用例
5. **LossLogger 设计**：时间戳+UUID 文件名、JSON Lines 格式、优雅降级、依赖注入——专业的 ML 实验追踪组件

### 项目核心问题

1. **评价器（Evaluator）可靠性不足**：作为训练管道的心脏，其核心逻辑存在空壳实现（`_compute_four_reward`）、信号丢弃（`blend_rewards` 取 max）、检测盲区（无法识别非连续棋型）等问题
2. **CNN 架构缺陷**：卷积层缺少空间降维，FC 瓶颈暴力压缩；BatchNorm 与均匀通道不兼容
3. **工程债务积累**：无 logging/配置管理/类型检查，dict 返回值无类型契约，多个入口各自操纵 sys.path

### 综合评分

| 维度 | 评分（5分制） | 说明 |
|------|-------------|------|
| 架构设计 | ⭐⭐⭐⭐ | 分层清晰，接口设计合理，但封装有泄漏 |
| 代码质量 | ⭐⭐⭐ | 风格统一但存在浅拷贝 bug、空壳实现等 |
| AI 算法 | ⭐⭐⭐ | 双向检测方向正确，但核心逻辑精度不够 |
| 模型设计 | ⭐⭐⭐ | FC→CNN 演进方向正确，但 CNN 架构有缺陷 |
| 工程实践 | ⭐⭐½ | 有测试和常量管理，但缺 logging/配置/类型 |
| 可维护性 | ⭐⭐⭐ | 模块可替换，但 dict 协议和文档不足 |

### 如果只能改 3 件事

1. **修复 `_compute_four_reward`**：从硬编码改为真正的递归计算，这是评价器核心逻辑 bug
2. **修复 `blend_rewards`**：从 max 改为加权融合（恢复 alpha 参数），让五连追溯早期步骤信号不被丢弃
3. **修复 `GomokuGame.__init__` 浅拷贝**：加入 deepcopy，一行代码修复一个定时炸弹
