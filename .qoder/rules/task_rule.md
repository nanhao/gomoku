# 任务报告

任务完成后必须生成任务详细报告，具体要求如下：

**报告内容必须包括**：
1. 需求内容 - 用户提出的原始需求
2. 解决思路 - 如何解决问题的整体思路
3. 执行过程 - 分解为哪些步骤执行，包括执行过程中遇到的问题和解决方式
4. 执行结果
5. 列出整个过程涉及到的文件（包括临时文件）

**报告文件存储要求**：
- 格式：markdown 文件（.md）
- 位置：task_reports/{year-month-day} 目录下
- 命名：简短的任务总结_{当天内递增序号} 如：task_reports/2025-12-31/为汇率数据计算趋势_1.md
- task_reports/{year-month-day} 目录（如果不存在）自动创建

# 工作边界
- 工作目录默认为当前目录加上 tests 目录
- 在工作边界之内的文件可以进行写操作，在工作边界之外的目录禁止进行任何写操作
- 开始任务之前，必须先报告该项任务的工作边界
- 如果不清楚工作边界，必须向用户确认
- 如果确实有很强的理由需要对工作边界之外的目录进行写操作，必须征得用户的同意

# 工作流程
1，阅读并理解需求，有不清晰或者疑惑时，阅读整个项目上下文，如何还不清晰，向用户确认
2，向用户确认需求理解和工作边界
3，进行详细设计。设计时遵循设计约束
4，编写测试用例，遵循测试约束
5，编码实现，遵循编码约束
6，跑通全量测试
7，生成任务报告
8，提交代码并 push，遵循提交约束

# 设计约束
- 必须输出设计文档
- 设计文档放在 {project_root}/design 目录下
- 设计过程中，遇到任何疑问，向用户确认。永远不要基于猜测做设计
- 对类文件进行设计时，只设计接口。不要设计私有方法
- 设计文档必须包含伪代码形式的主流程
- 设计文档必须包含主流程测试用例
- 设计文档要简练且精确，能够指导开发。不同的人根据设计文档来实现系统，最终结果应该是一致的

# 编码约束
- 使用 tdd，即测试驱动开发。
- 每个类都必须要有测试用例。测试覆盖率要求达到80%以上
- 先写测试用例，然后再写实现。
- 写完代码确保测试用例通过。
- 代码有丰富的注释。
- 以最严格标准按照设计文档进行编码。如果发现有任何模糊或不妥之处，应该立刻暂停，向用户确认。确认清楚后，立刻更新设计文档。
- 不要写超长的函数、方法、类和文件。

# 测试约束
- 每个类都必须要有测试用例。测试覆盖率要求达到80%以上
- 将所有的测试用例分为两类：主流程测试用例和边缘测试用例
- 主流程测试用例专注于测试业务主流程，必须严格按照设计文档编写
- 边缘测试用例专注于测试非主流程的分支、边界条件和回归发生过的 bug
- 主流程测试放在 primary 子目录下，边缘测试用例放在 edge 子目录下

# 修复任务约束
- 修复 bug 后，添加测试用例以覆盖此 bug 的发生场景，并跑通测试

# 提交约束
- 如果有新建用于测试用例的临时数据目录，加到 .gitignore
- 只提交本次任务修改的文件
- 如果提交时发现有预期外的文件因不明原因被修改，立刻暂停并向用户报告
